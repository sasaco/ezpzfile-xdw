# XDW Editor（VS Code の拡張、`vscode/`）

[EZPZ File XDW](https://github.com/ezpzfile/ezpzfile-xdw) のエディタ（`../web`）を、VS Code の Custom Editor の webview で動かす拡張です。DocuWorks の文書（`.xdw`）とバインダー（`.xbd`）を VS Code（ブラウザの code-server を含む）のタブで開き、見て、アノテーションを付け、保存します。

富士フイルムビジネスイノベーション株式会社とは関係ありません。DocuWorks は同社の商標です。

Marketplace・Open VSX には載せていません。この repo の release の `.vsix` を手で入れます。

## すること

- `.xdw` と `.xbd` を既定でこの画面に開く（Custom Editor `xdwEditor.document`、Explorer の右クリック「XDW Editor で開く」、コマンド `xdwEditor.openInScreen`、ターミナルからは `code <ファイル>`）。
- 上流のエディタを載せる（上流のファイルで変えたのはサムネイルの描き方の 1 か所だけ。ほかに、組み立てるときに開く前の確かめの時間を書き換え、後ろに足すスクリプトで遠いページの描いたものを捨てる。下の「作り」）。できることは上流と同じ：ページをめくる、文字の選択・コピー・検索、アノテーション、ページの操作、`.xdw`／`.xbd` の保存、PDF・テキストの書き出し。エンジンは webview の中の WebAssembly で、ファイルは外に送られない。
- **読み込み中の表示**：文書が画面に出るまで、まん中にクルクル回る印と 1 行の説明を出す。拡張がファイルを読んで webview に送っている間は「ファイルを読み込んでいます…」、エディタが開く前にファイルを確かめている間（1 秒あまり）は「文書を確かめています…」。上流のエディタだけだと、その間はファイルを置くよう勧める空の画面のままで、何も動かない。文書が出たとき、開けなかったときに消える。
- **開く前の確かめは 1 秒**：上流のエディタは、ファイルを開く前に別のスレッド（Worker）で開いてみて、ページを 8 秒のあいだ描けるだけ描く。エディタはそれを待つので、描くのに 8 秒より長くかかる文書は、どれも 8 秒遅れて出る。この拡張では 1 秒にした（36 MB・330 ページの `.xbd` が 11 秒から 4 秒、62.5 MB・5417 ページが 14 秒から 8 秒）。Worker で開いてみること（DocuWorks のファイルでない・壊れている・保護されている・大きすぎる）と、初めの何ページかを描いてみることは変わらない。**その先のページは、文書が出る前には試さない**（上流も、8 秒で届かないページは試さない）。
- **描けないページが 1 つあっても、文書は開く**：エンジンは、自分の上限を超えるページ（1 ページに 500 万点を超える図形など）を、エラーを返して断る。エンジンは動き続けるので、エディタはそのページに来たときに「N ページを表示できませんでした」と出し、ほかのページは出す。ところが上流の開く前の確かめは、試したページが 1 つでも描けないと、ファイルごと「開けませんでした」と断る。この拡張では、確かめがそういうページを通す。エンジンが止まる（trap）ページは、今までどおり断る。描けないページのある文書は、PDF の書き出しはできない（上流のまま）。
- **検索とテキストの書き出しで、エンジンが止まらない**：エンジンは、ページごとに求めたものを「忘れろ」と言われるまで持つ。上流のエディタは、ページを描いたあとは忘れさせるが、ページの文字を読んだあとは忘れさせない。検索はページを順に読んで探し、テキストの書き出しは全ページを読むので、スキャンしたページのある文書では 50 ページあまりでエンジンのメモリ（上限 1 GiB）を使い切って、エンジンが止まっていた。この拡張では、ページの文字を読んだらそのページを忘れさせる。
- **描けないものがあるページを知らせる**：エンジンは、知らない形で入っている図（エンジンの知らない描画の種類のもの。0.1.6 までは、DocuWorks が大きな画像を入れた画像アノテーション（描画の種類 10）がそうだった）を、そのアノテーションごと描かずに飛ばし、ページはそれ抜きで出る。上流のエディタは何も言わないので、図が欠けていても気付けない。この拡張では、そういうページが文書の中で初めて画面に描かれたとき、「1・2 ページに、この画面では表示できないもの（4 か所）があります。…DocuWorks で見てください。」と 10 秒出す（近くで一緒に描かれたページは 1 つの知らせにまとめる。同じページは文書を開き直すまで二度言わない。サムネイルと印刷では言わない）。数えるのはページの本文・アノテーションのうち丸ごと描けなかったものだけで、図の中の描かないレコード（DocuWorks の内部のコメントなど）は数えない。PDF の書き出しでも、その図は抜ける。
- **DocuWorks 9 の画像を、DocuWorks と同じに出す（0.1.6）**：DocuWorks 9 でペイントなどから貼った画像（描画の種類 7）は、0.1.5 まで上下逆さまに出ていた。画像ファイルをページにしたもの（DocuWorks 9 の高圧縮、描画の種類 11）は描かれず、上の知らせが出ていた。0.1.6 では、どちらも DocuWorks と同じ向き・同じ画素で出す。この画面で貼った画像も、DocuWorks で正しい向きに出る。**0.1.5 までのこの画面で貼った画像は、ファイルの中に上下逆さまに入っていて、DocuWorks では逆さまに出ていた。0.1.6 からはこの画面でも同じく逆さまに見える**（貼り直せば直る）。
- **DocuWorks が大きな画像を入れた画像アノテーションを出す（0.1.7）**：CAD や Excel から貼った図など、画素の多い画像アノテーション（描画の種類 10）を、DocuWorks と同じ画素で描く。0.1.6 までは描かれず、上の知らせが出ていた。種類 10 は可逆の符号（上の行・左の画素から写す連長と、新しい色の差分）で、形式は fork の `docs/spec/XDW-FORMAT.md` の 5.6。
- **画像を画面でにじませない（0.1.7）**：回転も裏返しもなく、自分の大きさ（1 画素以内）で描かれる画像は、四捨五入した位置に、なめらかにせずに置く（DocuWorks の描画と `xdw_png` と同じ）。0.1.6 までは、画像が画素の境目に乗らないと縁がにじんでいた。
- **JPEG の画像を DocuWorks と同じ色で出す（0.1.8）**：JPEG のページ（描画の種類 5）・高圧縮のページ（種類 11）の背景・EMF の中の JPEG（ビットマップの JPEG を含む）を、エンジンが DocuWorks と同じ展開（libjpeg-turbo の速い整数の IDCT と、同じ色の変換）で開き、その画素を画面に渡す。0.1.7 まではブラウザが展開していて、DocuWorks と色が最大 5〜6 ずれていた。エンジンが開けない JPEG は、今までどおりブラウザが展開する。A4・300 dpi のカラーの JPEG のページは、描くたびに 0.1 秒ほど余計にかかり、描いている間メモリが 1 ページあたり約 100 MB 増える（同時に描くページの数だけ増える。エンジンの wasm のメモリは一度増えるとその大きさのまま使い回す）。
- **エンジンが止まったら、そう知らせる**：エンジンが止まる（メモリ不足など）と、そのあとは何を頼んでも失敗する。上流のエディタは、出ているものを出したまま、何も言わずに描かなくなり、保存もできなくなる。この拡張では、止まったときに画面の上に知らせを出し、「開き直す」のボタンで文書を読み込み直す（保存していない変更は失われる）。
- **遠いページは、描いたものを捨てる**：上流のエディタは、見えているあたりに来たページを描き、そのあとずっと持ち続ける（canvas と文字の層）。長い文書を読み進めると、見たページの分だけメモリが増える。この拡張では、見えているところから 2400px より遠くなったページの描いたものを捨て、戻ってきたら描き直す。文字を選んでいるページは、選んでいる間は捨てない。検索は、捨てたページも描いて探す。
- **保存**：上流のエディタはファイルをブラウザのダウンロードとして保存する。この拡張では、そのバイトを VS Code の保存の画面に渡す。開いている文書のフォルダと、エディタが付けた名前を勧める。元と同じ名前を選ぶと上書きで、VS Code が確かめる。名前を選ぶまで何も書かない。
- **印刷**：VS Code の webview は `window.print()` を無視するので、印刷はできない。エディタの印刷を押すと、その旨を知らせて「PDF で保存」を勧める（保存した PDF を印刷する）。
- 画面の言葉は VS Code の表示言語に合わせる（日本語なら日本語、ほかは英語）。
- 読み取り専用の Custom Editor：文書・元に戻す・保存はエディタが持つので、VS Code の未保存の印は出ず、**保存していない変更があるタブを閉じても VS Code は確かめない**。
- 開いている文書をほかで書き換えても、画面は気付かない。開き直せば新しい中身になる。
- 外のネットに出るのは上流と同じ 2 つだけ：画面の書体の CSS（jsdelivr の Pretendard。取れなければ PC の書体）と、PDF のページを挿入するときの pdf.js（cdnjs）。webview の CSP はこの 2 つだけを通す。

## 作り

| | |
|---|---|
| `scripts/assemble.mjs` | 上流の `web/editor.html`・`editor/i18n.js`・`editor/app.js` と wasm-bindgen の glue を、webview 用に組み立てる（上流の `web/build.sh` と同じ組み立て）。スクリプトは別ファイルにし、`.wasm` は URL から読む。`app.js` の `const CHECK_MS = 8000;`（開く前にページを描いてみる時間）を、組み立てた先で `CHECK_MS`（1000）に書き換え、確かめがページを描く 1 行を、エンジンが断ったページを通すもの（`CHECK_DRAW`）に書き換える。読んだファイルの改行は LF にそろえる（Windows の CRLF のチェックアウトでも同じものができる） |
| `webview/host.js` | 上流の `editor/host.js` の代わりに入れる `HOST`。上流のものはエディタを枠に入れた Web ページ（ezpzfile.com）と話すが、webview では上の枠が VS Code 自身なので、それをそのページと見誤る。同じ形で、文書の受け取りと保存を拡張とやりとりする。読み込み中の表示（`HOST.loading`）と、エンジンが止まったときの知らせ（`HOST.engineStopped`）もここにある |
| `webview/tail.js` | `app.js` の後ろに足す数行。エディタの `download` を拡張に渡すものに差し替え、`window.print` を上の案内に差し替える。ページを描く `renderTo` を包んで、エンジンが描かなかったものの数（`render` の JSON の `notDrawn`。エンジンの `Display::objects_not_drawn`）があるページを知らせる。エディタがファイルを確かめる `checkFirst` と開く `openFile` を包んで、読み込み中の表示を切り替え、消す。ページを並べる `buildPages` を包んで、遠くなったページの canvas と文字の層を捨てる（エディタは「描いていない」ページを、近くに来たときに自分で描き直す）。エンジンの呼び出し（`XdwDoc` のメソッド）を包んで、ページの文字を読んだらそのページを忘れさせ、エンジンが止まった（trap）ら知らせる |
| `src/extension.ts` | Custom Editor。文書のバイトを webview に渡し、保存を受けて保存の画面を出す。文書を読めなかったら webview に知らせる（読み込み中の表示が残らないように）。「開き直す」を受けたら、webview を読み込み直す |
| `src/html.ts`・`src/save.ts` | webview の CSP とページ、保存の名前と種類 |

上流のファイルで変えたのは 1 か所だけです。`web/editor/app.js` のサムネイル（左のページの一覧）を、一覧の見えているあたりに来たときに描き、離れたら描いたものを捨てるようにしました。上流は文書を開いた直後に全ページ分を描いて持ち続けるので、数千ページのバインダーでは描き終わるまで何分もかかり、ブラウザのメモリを GB の単位で使います（一覧が隠れている幅の狭いタブでも同じ）。開く前の確かめの時間と、遠いページを捨てることは、上流のファイルを変えずに行っています（組み立てるときの書き換えと、`tail.js`）。上流を取り込んでサムネイルの変更が消えたとき、確かめが描けないページを通すこと、検索でエンジンが止まらないこと、止まったときの知らせも同じです。上流が `HOST` の形・`download`・`CHECK_MS` の行・確かめがページを描く行・ページの描き方（`buildPages`・`drawPage`）・検索とテキストの書き出しの文字の読み方を変えたときは、`tests/assemble.test.ts` が落ちます（組み立てるときに書き換える 2 行が変わると、ビルドも止まります）。

## ビルドとテスト

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129 --locked   # engine/Cargo.lock の wasm-bindgen と同じ版
npm --prefix vscode ci
npm --prefix vscode run typecheck
npm --prefix vscode test
npm --prefix vscode run package    # vscode/xdw-editor-<版>.vsix（--skip-wasm で前の WASM を使う）
```

Windows でも同じ手順で通ります（改行が CRLF のチェックアウトでもよい）。Rust が GNU 版（`x86_64-pc-windows-gnu`）で MinGW を入れていない PC では、`cargo install wasm-bindgen-cli` が `dlltool` のところで失敗します。そのときは wasm-bindgen の release にある同じ版の `wasm-bindgen-0.2.129-x86_64-pc-windows-msvc.tar.gz` の `wasm-bindgen.exe` を PATH に置きます（できる glue は、CI が `cargo install` したもので作る glue とバイトが同じでした）。

release：タグ `vscode-v<package.json の version>` を push すると、`.github/workflows/vscode-release.yml` が `.vsix` と `SHA256SUMS.txt` を GitHub release に出します。

## 入れ方

```sh
code-server --extensions-dir <dir> --install-extension xdw-editor-<版>.vsix
```

## 確かめたこと

2026-11-11 に code-server 4.145.2（macOS、Intel、Chrome）で、設計計算書の `.xdw`（1.8 MB、32 ページ）と `.xbd`（12.9 MB、561 ページ）を使って確かめた：既定で画面に開く、ページの描画と文字の層、検索、文字の選択、四角形のアノテーション、保存（保存の画面が文書のフォルダと名前を勧め、別の名前で書ける。元と同じ名前では VS Code が上書きを確かめる。取り消すと何も書かない）、PDF の書き出し、PDF のページの挿入（cdnjs の pdf.js）、印刷の案内から PDF の保存。どの操作でも、保存の画面で名前を選ぶまで元のファイルのバイトは変わらない。

2026-11-14 に code-server 4.145.2（Windows、画面なしの Edge、表示倍率 150%）で、設計計算書の `.xbd`（62.5 MB、37 文書・5417 ページ）を使ってサムネイルを確かめた（エンジンは 0.1.0 の `.wasm` のまま、`editor.js` だけを組み立て直した）。変える前は、一覧の見える幅の広いタブで、開いて 223 秒たっても 5417 枚のうち 1306 枚しか描き終わらず、ブラウザのメモリは 1.9 GB から 3.4 GB に増えて、まだ増えていた。一覧が隠れる幅の狭いタブでも 5417 枚を全部描き、174 秒かかって 1.4 GB が 3.4 GB になった。変えた後は、描いて持っているのは見えているあたりの 5〜8 枚だけで、メモリは 1.1 GB のまま増えない。一覧を端から端まで動かして戻しても同じで、見えているサムネイルはどこでも描かれている。幅の狭いタブでは 1 枚も描かない。330 ページの `.xbd` で、見えているページと一覧の遠くのページを回転し、元に戻して、サムネイルの向きと一覧の中の場所が合うことも見た。

同じ日に同じ code-server で、読み込み中の表示（0.1.2）を確かめた。36 MB・330 ページの `.xbd` は「ファイルを読み込んでいます…」が 2.7 秒まで、「文書を確かめています…」が 10.9 秒までで、消えるのと同時に文書が出た。62.5 MB・5417 ページは 4.1 秒まで、13.9 秒まで。1 MB/秒に絞った回線では、23 MB の `.xbd` で「読み込んでいます」が 43 秒続いた。壊れたファイルでは表示が消えて「開けませんでした: …」が出て、空の画面に戻る。ほかのプロセスが握っていて拡張が読めないファイルでは、表示が消えて VS Code がエラーを知らせる。文書を開いたままエディタの「開く」で別の文書を開くと、開いている文書の上に「確かめています」が出てから替わる。日本語の文言は、拡張の写しで言語を `ja` に決めて見た（VS Code の表示言語を日本語に切り替えた状態では見ていない）。release の 0.1.1・0.1.2 の `.vsix` の中身は、確かめたものとバイトが同じ。

0.1.2 までは、Windows の `core.autocrlf=true` のチェックアウトで `scripts/build.mjs` と `tests/assemble.test.ts` が通らなかった（組み立てが LF の改行を前提にしていた）ので、上の確かめは、同じ中身を LF で取り出した写しでビルドしてテストした。0.1.3 で、読んだファイルの改行を LF にそろえるようにした。CRLF のチェックアウトのまま、テスト 21 件が通り、`npm --prefix vscode run package`（エンジンを WebAssembly にするところから `.vsix` まで）が通る。できた `editor.js`・`editor.html` に CR は入らない。

同じ日に同じ code-server で、0.1.3 の 2 つを 0.1.2 と比べて確かめた（エンジンは 0.1.2 の `.wasm` のまま）。**開くまでの時間**（頼んでから 1 ページ目が出るまで）：36 MB・330 ページの `.xbd` が 11.0 秒から 4.0 秒、62.5 MB・5417 ページが 13.7 秒から 7.8 秒、2.3 MB・30 ページは 1.9 秒のまま。**読み進めたときのメモリ**（62.5 MB の `.xbd` を 1 ページ目から 300 ページ目まで 1 ページずつ送る。幅の広いタブ、ページは 100%、表示倍率 150%）：0.1.2 は 301 ページ分の canvas（2,647 MB）を持ち続け、ブラウザ全体（private）が 1.3 GB から 5.4 GB になった。0.1.3 は持っている canvas が 5 ページ分（38 MB）のままで、ブラウザ全体は 1.3 GB から 2.5 GB。0.1.3 で 800 ページ目まで送ると 3.2 GB で、canvas のほかにゆっくり増えるものが残っている（どこかは分かっていない。エンジンのメモリは 365 MiB から増えない）。どこで止めても、見えているページは描かれている。1 ページ目に戻る、途中に飛ぶ、遠くのページにある文字を検索する（そのページを描いて、選んで、そこへ移る）、文字を選んだページが遠くなっても選んだ文字が残る、拡大、一覧から遠くのページを回転して元に戻す、を見た。5417 ページの文書を開いた直後に、全ページを 1 枚ずつ調べて 20 秒止まる誤りが途中であり、描いていないページには触らないようにして直した（上の 7.8 秒は直した後）。

0.1.3 まで：62.5 MB の `.xbd`（スキャンしたページがある）で検索するとエンジンが止まる（`unreachable`）。
